# 同步协议与冲突策略

## 状态

客户端文档同时维护：

- `local_revision`：每次本地事务保存递增。
- `remote_revision`：最近确认的云端版本。
- `outbox.operation_id`：一次可幂等重放的上传任务。

每次编辑会用最新文档替换尚未发送的 `put-document`，所以离线期间不会积累成千上万个
中间版本；本地快照仍独立保留最近 30 个恢复点。

## 推送

1. 上传所有 `remote_state=pending` 的图片，路径按 SHA-256 去重。
2. 客户端发送完整文档、资源哈希清单和 `baseRevision`。
3. 服务端在 PostgreSQL 行锁事务中比较版本。
4. 相同 operation ID 返回 `alreadyApplied`；版本相同则写入下一版本；否则返回冲突及
   完整远端文档。

完整文档而非细粒度操作日志是刻意的选择：当前上限 5000 节点，压缩后的 JSON 较小，
完整快照更容易校验、恢复和跨版本迁移，也避免旧客户端产生无法重放的结构操作。

## 拉取

只有本地 outbox 为空时才允许应用远端文档。应用顺序是：

1. 校验远端文档。
2. 下载并校验所有缺失图片的 MIME 签名与 SHA-256。
3. 为当前本机文档创建 SQLite 快照。
4. 在一个事务内切换文档和远端版本。
5. 通知 WebView 重新载入。

## 冲突

发现版本冲突时，客户端把本机与云端 JSON 同时写进 `conflicts`，再将本机当前版本
基于最新远端版本重新排队。用户可以在云同步面板中：

- 保留本机版本：确认冲突记录，本机版本继续同步。
- 采用云端版本：先快照当前本机内容，再切换为保存的远端副本。

任何路径都不会丢弃两边内容。后续可以在不改变协议的情况下加入字段级三方合并。

## 重试

- 网络/5xx：2、4、8 秒指数退避，上限 300 秒；任务持久化，重启继续。
- 401：刷新访问令牌并在下一轮重试。
- 409/版本冲突：保存冲突副本并重基。
- 资源上传：内容寻址且 PUT 幂等，可安全重复。
